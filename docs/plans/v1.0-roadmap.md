## 1. 关键洞察：穿透聚合是巴菲特自己的发明，而且必须做在事实层

### 1.1 "Look-through earnings" 是巴菲特 1990 年致股东信里的原创概念

他持有一堆公司的部分股权，会计利润只体现分红，于是他自己定义了「穿透盈余」：
按持股比例把被投公司的留存收益加回来看。**用穿透法评估 QQQ 不是把方法硬套在 ETF 上，
就是他本人处理"我拥有一百家生意的一部分"的标准做法。**这解决了合规和方法论正当性两个问题。

### 1.2 聚合只能做在事实层（DSL 层做不了，这反而是好消息）

决策 DSL 的算子白名单是
`eq/neq/gt/gte/lt/lte/date_*` + `exists` + `all/any/not`，操作数只能是
`{fact_id}` / `{output_id}` / `{literal}`（`literal` 必须是标量，数组直接拒），
条件层不支持算术。工具层的 `sum/mean` 吃的是固定 arity 的操作数列表，不是集合。

**结论：DSL 永远不可能对 N 个持仓做加权聚合。**
所以聚合必须在 `grounding-adapter` / 新的 `funds.mjs` 里做，产出**一个**
`financial.owner_earnings` 事实（带 `derivation: "rederived"` + `calculation_hash` + `coverage_weight`）。

**而这正是好消息：** 一旦事实层把 QQQ 的穿透 `financial.owner_earnings` 供上，
**26 个 pack 一个字节都不用改就能在 ETF 上执行。** 不需要 instrument 条件化的 pack 变体，
不需要动 schema，不需要重签 hash，不需要动选席回执的 pack_hash 审计链。

（我评估过四种 instrument 条件化方案：pack 内多份 policy 8-10 天 / `required_fact_types` 改 map
10-14 天 / 平行包集 15-20 天且撕裂审计链 / `research_model` 做成 typed fact 走 eligibility 3-4 天。
但做完事实层之后，前三种都不需要了，第四种只在"某方法必须显式拒绝某类标的"时才用。）

#### A2. `mcp/lib/funds.mjs` — ETF 持仓与穿透聚合

**已验证可用的发行商端点（全部免密钥，四条 URL 都是新路径，网上流传的旧地址已失效）：**

```bash
# iShares（IVV/IWM/EFA/AGG/TLT/HYG…）日度 T-1
https://www.ishares.com/us/products/239726/x/latest-holdings.csv

# Vanguard（VOO/VTI…）仅月末，每页 500 条
https://investor.vanguard.com/investment-products/etfs/profile/api/VOO/portfolio-holding/stock
```

**必须写进代码的反爬陷阱（每条都是实测的，漏一条就静默出错）：**

1. **iShares 旧 `.ajax` 路径是静默陷阱** —— 仍返回 `HTTP 200` + `Content-Type: text/csv`，
   但 body 是 2.2MB 的 HTML 产品页，换任何 UA 都一样。**必须校验首行内容，不能只看状态码。**
2. **Invesco 的 UA 逻辑是反的** —— `www.invesco.com` 发 Chrome UA 或空 UA → `HTTP 406` 零字节；
   发默认 `curl/8.x` 或 `node-fetch` → 200。**千万别伪装浏览器。**
3. **Invesco 参数陷阱** —— 漏 `interval=daily` 拿到 3 天前的旧数据；误加 `loadType=initial`
   静默截断成前 10 条；`idType=ticker` 只对 QQQ 有效，统一用 CUSIP。
4. Vanguard 响应里的 `next` 指向已废弃的 `api.vanguard.com`，翻页要自己拼
   `?start=501&count=500` 打在 `investor.vanguard.com`。
5. SEC 任何请求必须带 `User-Agent: app contact@email`，否则 403。

**费率 / AUM / NAV / 份额：**
- iShares product-screener 一次拿 532 只基金的 `fees` / `navAmount` / `totalNetAssets` / `cusip`
- SSGA fundfinder 一次拿 180 只 SPDR 的 `ter` / `nav` / `aum`（份额 = aum/nav）
- **Vanguard 和 Invesco 没有 AUM/份额端点**（Invesco 的 `/nav`、`/profile` 全 501）→
  用持仓市值求和，或 SEC N-PORT 的 `netAssets` 兜底

**资金流（无免费直接源，必须推导）：** `flow = Δshares_outstanding × NAV`。
实测验证过：IVV 份额 2026-07-24 的 1,167,300,000 → 07-27 的 1,167,700,000，
Δ+400,000 股 × NAV 741.66 ≈ 净流入 $296.7M。
**局限**：只有 iShares 和 SSGA 有日度份额，Vanguard/Invesco 没有 → 那两家的 flow 记为 gap，不许估。

**SEC N-PORT 兜底（重要更正：是季度不是月度）：**
表单名叫 "Monthly Portfolio Investments Report"，但公开披露实际**季度**，滞后 50-59 天。
另一个坑：`company_tickers.json` 里**查不到 IVV 和 VOO**（它们是信托下的 series），
必须用 `company_tickers_mf.json`（IVV→CIK 1100663/S000004310，VOO→CIK 36405/S000002839）。

**新增 typed facts：**
```
fund.holdings_as_of  fund.top_ten_weight  fund.sector_concentration_hhi
fund.expense_ratio   fund.aum             fund.shares_outstanding
fund.flow_20d        fund.premium_discount fund.tracking_difference(nullable)
fund.lookthrough_coverage_weight
```

**穿透聚合（本方案的核心）：** 对前 N 大持仓（覆盖权重 ≥60%）批量取基本面，
按权重聚合成**单个**经营公司事实：`financial.owner_earnings`、
`financial.return_on_equity_10y`、`valuation.revenue_growth` 等。
每个聚合事实必带 `lineage.calculation_hash` + `fund.lookthrough_coverage_weight`。

**硬规则写进代码，不是写进 prompt：** 覆盖权重 < 50% 时**不生成**任何 look-through 派生事实，
只记 diagnostics。现在这条只是 prompt 里一句话，模型可以无视。

**绝不做的事：** 把成分股财报相加成"ETF 营收/EPS"。加权只允许出现在比率型指标，
且 `ratio_denominator` 必须写明加权口径。

### 支柱 B — 真方法模型（"有没有意义"的分水岭）

#### B0. 操作纪律（不遵守每次都会红）

pack 是 100% 机器生成的，**手改无效**——生成器会在内存里重建全部文件逐字节比对。
唯一合法路径：改 `data/persona-v3-build-specs.v1.mjs` + `knowledge/solo-test/persona-v3-solo-test-formulas/`
+ 生成器，然后：

```bash
npm run persona:solo-test:build       # 26 个 pack 全量重生成
npm run persona:ai-simulations:write  # 8 个仿真 run 重生成
npm run check                         # selfcheck 三道闸 + 全测试
```

另外：动 `runtime.mjs` / `deterministic-executor.mjs` / `typed-facts.mjs` / `registry.mjs`
这四个文件中的任何一个，都必须重跑机器仿真（它们的字节 hash 被绑进仿真树）。

#### B1. 生成器改造：让 spec 里的设计真正落地

`scripts/lib/persona-v3-solo-test-packs.mjs:299-348` 现在硬编码
`eligibility: { all: [] }`、`hard_vetoes: []`，把 build-spec 里已经写好的
`veto_families` 和 `native_decision_contract.eligibility_facts` 全丢了。改成从 spec 生成。

**一个必须绕开的陷阱：** 当前 `scoring.min_coverage = 1`，
**任何一条规则 uncomputable → 整席直接 `out_of_scope`**。
所以方法判据要走 `eligibility` / `hard_vetoes`（它们有独立的 uncomputable 出口），
不要全塞进 scoring rules，否则缺一个字段就整席哑火——这正是现在 25 席弃权的机制。

#### B2. 写真公式，替换 identity 桩

DSL 条件层不支持算术，所以每个判据要拆成"工具算数 + 条件比数"两步。
可用算子：`add subtract multiply divide sum mean min max abs negate clamp`（标量，固定 arity）。
条件层支持 **fact vs fact 直接比较**（实测通过），这是关键——
"盈利收益率 > 国债收益率" 可以直接写成两个 fact 的 `gt`，不需要先算差值。

#### C1. 五段式第一人称（`voice_mode`）

`position_intent` **由冻结立场机械派生**：建 `stance → allowed intents` 表，

#### C4. 命名与合规

## 6. 一句话

当前 26 席里只有 1 席能执行，而那 1 席的"方法"是 `identity(x) > 0`。
**三层都是空的：事实层缺 92%，方法层是脚手架，表达层是机器诊断。**
顺序不能反 —— 先补事实（不碰 pack，零风险），再写真方法（这是"有没有意义"的分水岭），
最后做表达。做完前两层，巴菲特看 QQQ 会说"盈利收益率 3.03%，国债 4.69%，我不会买"，
而不是"这不归我管"。
